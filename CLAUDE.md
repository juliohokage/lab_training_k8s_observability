# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A GitOps lab (single local cluster on WSL2) reconciled by **Flux** from `main` of `github.com/juliohokage/lab_training_k8s_observability`. There is no application code, build or test suite: everything is Kubernetes YAML, Kustomize and Grafana dashboard JSON. Changes take effect only once pushed to `main` and reconciled by Flux.

Two goals:
1. An observability stack: OpenTelemetry collectors feeding the Victoria* backends, shown in Grafana.
2. Learning **Crossplane v2** by orchestrating tenant onboarding. The roadmap is in `docs/tenant-onboarding-roadmap.md`.

## Validating changes

- Render a layer locally before pushing: `kubectl kustomize <dir>`, for example `kubectl kustomize infrastructure/controllers`.
- After push: `flux reconcile source git flux-system`, then `flux get kustomizations` / `flux get helmreleases -A`.
- Grafana dashboards are plain JSON files. Check them with `jq . <file>` before committing.

## Flux layering (the big picture)

`clusters/lab/kustomization.yaml` declares Flux Kustomizations, each pointing at a top-level directory. Each has `wait: true` and `prune: true`, and `dependsOn` controls the order:

```
infra-controllers (infrastructure/controllers)  operators, backends, Grafana: anything installing CRDs or long-lived services
  └─ infra-configs (infrastructure/configs)     CRs needing those CRDs: VMCluster, OpenTelemetryCollector gateway+agent
       └─ apps (apps)                           telemetrygen, which emits test signals

crossplane (crossplane)                         Crossplane 2.x HelmRelease
  └─ platform (platform)                        Providers, Functions, XRDs, Compositions (currently empty)
       └─ tenants (tenants)                     one namespaced XR per tenant (currently empty)
```

Put a new resource in the layer that matches what it depends on. For example, a CR whose CRD comes from an operator goes in `configs`, not `controllers`. Every new file must be listed in that directory's `kustomization.yaml`, or Flux ignores it. `clusters/lab/flux-system/gotk-*.yaml` are generated by Flux: do not edit them.

## Telemetry data flow

- **Agent** (DaemonSet, `infrastructure/configs/opentelemetry/collector-agent.yaml`) collects kubelet_stats, host metrics and scrapes `prometheus.io`-annotated pods, then sends OTLP to the gateway.
- **Gateway** (Deployment, `collector-gateway.yaml`) receives OTLP, runs the `k8s_cluster` receiver (single replica to avoid duplicates), and exports over OTLP HTTP:
  - metrics to **VMCluster** `vminsert-vmc.monitoring:8480` (read through `vmselect-vmc:8481/select/prometheus`);
  - logs to **VictoriaLogs** single `vls-victoria-logs-single-server.logging:9428`;
  - traces to **VictoriaTraces** single `vts-vt-single-server.tracing:10428` (read through its Jaeger API).
- Container logs reach VictoriaLogs separately, through the `victoria-logs-collector` HelmRelease, not through OTel.
- RBAC for the receivers lives in the same file as each collector, as a ClusterRole. Extend it when adding a receiver that needs to watch new kinds.

**Multi-tenancy:** all three backends separate tenants only by the `AccountID` / `ProjectID` HTTP headers. Everything currently uses `0:0`, on both write (exporter headers) and read (Grafana datasource headers). There is no vmauth/VMUser, so there is no real isolation. This is intentional for the lab. The planned convention is tenant ID = `AccountID`.

## Grafana

- The datasources (`victoriametrics`, `victorialogs`, `victoriatraces` UIDs) are provisioned in `infrastructure/controllers/grafana/helmrelease.yaml` values.
- Dashboards are JSON files in `infrastructure/controllers/grafana/dashboards/`. Each one needs a `configMapGenerator` entry in `infrastructure/controllers/kustomization.yaml`, with the label `grafana_dashboard: "1"` and `disableNameSuffixHash: true`. The Grafana sidecar loads them.
- Panels reference datasources by UID. The Crossplane dashboard filters on the `namespace` label of controller-runtime / crossplane metrics.

## Working agreement on Crossplane

The user is learning Crossplane hands-on. In `platform/` and `tenants/` (XRDs, Compositions, Functions, Providers, XRs), **guide and explain, but do not write the Crossplane code** unless explicitly asked. Claude may write the observability side: Grafana dashboards, collector receivers/RBAC, kube-state-metrics config. Target Crossplane v2 conventions: namespaced XRs (no claims), namespaced `.m.` managed resources, pipeline-mode Compositions. Later, the platform API will be shipped as an OCI Configuration package built from GitHub.
